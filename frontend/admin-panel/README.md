# Admin Panel — план работ

Админ-панель — интерфейс сотрудников управляющей компании для работы с объектами, помещениями, пользователями и подключёнными IoT-устройствами. Она отвечает за представление данных и действия пользователя; правила доступа и связь с IoT-платформами остаются на backend-сервисах.

## Технологии и текущая конфигурация

- Nuxt 3 и Vue 3, TypeScript, Vite.
- Tailwind CSS 4 через `@tailwindcss/vite`; базовые стили и CSS-переменные находятся в `assets/css/tailwind.css`.
- `shadcn-nuxt` и Reka UI для доступных UI-компонентов; `lucide-vue-next` для иконок.
- Pinia и VueUse для состояния и Vue-композиций.
- Vee Validate + Zod для форм и схем валидации.
- TanStack Vue Table для таблиц, Unovis для графиков, `xlsx` для экспорта.
- Базовый URL приложения настроен как `/admin`; публичная конфигурация предусматривает `apiUrl` и `wsPort`.

Устанавливайте пакеты из каталога `frontend/admin-panel`. `package.json` содержит скрипты `dev`, `build`, `generate`, `preview`, `start` и `test`. В репозитории сейчас нет lock-файла npm; выберите npm и добавьте сгенерированный `package-lock.json`, чтобы команда использовала воспроизводимые версии зависимостей.

## Сначала согласовать с командой

До подключения данных договоритесь с авторами auth и IoT-интеграции о:

- URL и версиях API, способе передачи access token и обновлении сессии;
- ролях и доступных разделах, а также том, как API ограничивает данные по организациям/объектам;
- формате ошибок, дат, пагинации, фильтров и статусов устройства;
- минимальном API для списка объектов/устройств, карточки состояния, истории сигналов и отправки команды;
- поведении при недоступности сервиса и устаревших данных.

Браузер не должен обращаться прямо к Ujin и не должен хранить секреты IoT-платформы. Клиентские проверки ролей управляют отображением интерфейса, но реальную авторизацию каждой операции выполняет backend.

## Порядок первых задач

### 1. Подготовить старт приложения

`app.vue` сейчас пустой, а `nuxt.config.ts` подключает модули `core`, `dashboard`, `certificates`, `events`, `integrations`, `payslips`, `news` и `users`. В файловой структуре пока есть только `modules/core`; страницы, layout и точка входа ещё не созданы.

Сначала:

1. согласуйте, какие разделы входят в хакатонный MVP;
2. создайте корневой layout и базовую страницу/маршрут;
3. реализуйте либо добавьте безопасные минимальные entrypoint-файлы для модулей, перечисленных в Nuxt-конфигурации, либо временно подключайте только реально существующие модули;
4. проверьте, что Nuxt поднимается и навигация работает до начала наполнения разделов.

Не оставляйте ссылки на несуществующие модули: Nuxt пытается импортировать каждый путь из `modules`.

### 2. Сделать полезный вертикальный сценарий

Рекомендуемый MVP для УК:

1. вход/выход и отображение текущей роли;
2. выбор доступного объекта;
3. список устройств объекта с состоянием, доступностью и временем последнего обновления;
4. карточка устройства с сигналами и короткой историей;
5. отправка одной безопасной команды с подтверждением результата и понятной ошибкой.

Начните с одного типа устройства и согласованного API. Для разработки можно использовать локальные данные или эмулятор из `backend/emulators`, но пометьте фиктивные данные и не выдавайте их за live-состояние.

### 3. Ввести соглашение по модулям

Конфигурация ожидает функциональные модули. Предлагаемая организация каждого модуля:

```text
modules/<module>/
  module.ts              # регистрация Nuxt-модуля/плагинов, если требуется
  pages/                 # страницы раздела
  components/            # компоненты, используемые только этим разделом
  composables/           # загрузка данных и состояние раздела
  types/                 # типы API и представления раздела
```

Общие элементы размещайте в корневых `components/`, `composables/`, `utils/`, `types/`. Один компонент — одна понятная ответственность; бизнес-правила доступа не дублируйте на клиенте.

В проекте есть `scripts/setup-module-links.sh`, который создаёт ссылки страниц модулей в `pages/`. Он удаляет уже существующие символические ссылки в целевой `pages/` перед созданием новых. Используйте его только после чтения скрипта, появления модульных страниц и проверки, что целевые ссылки принадлежат этому механизму. На Windows потребуется Git Bash/WSL; для хакатонного MVP можно выбрать обычную структуру страниц Nuxt без генерации ссылок.

### 4. Настроить API-клиент и состояния интерфейса

Используйте `runtimeConfig.public.apiUrl` как базовый URL и настройте его через локальное окружение/конфигурацию запуска. Не вшивайте адрес тестового/production API в компоненты. Вынесите HTTP-вызовы в composables или отдельный клиент, добавьте общую обработку 401/403/5xx и типизированные DTO после согласования OpenAPI.

Для каждой страницы предусмотрите состояния загрузки, пустого результата, ошибки, недоступности устройства и устаревшей телеметрии. При отправке команды блокируйте повторный клик до завершения запроса и показывайте пользователю подтверждённый сервером результат.

### 5. Соблюдать базовую безопасность и UX

- Не коммитьте `.env`, токены и реальные данные жителей.
- Не помещайте токены IoT-платформ в браузер.
- Скрытая кнопка не является проверкой доступа: backend должен проверять роль и доступ к конкретному объекту.
- Показывайте ясные статусы связи, время последнего обновления, единицы измерения и подтверждение команды.
- Используйте семантическую разметку, клавиатурную навигацию, контрастные состояния и подтверждение опасных действий.
- Не отправляйте команду, пока пользователь не выбрал устройство и действие однозначно.

## Пакеты и конфигурация: на что обратить внимание

- `components.json` задаёт алиасы shadcn-vue на `@/components`, `@/composables`, `@/utils`, но также указывает `@/lib/utils` и `@/lib`; каталог `lib/` сейчас не виден, зато есть `utils/`. Перед генерацией shadcn-компонентов согласуйте алиасы с `nuxt.config.ts` и фактическими каталогами.
- `tsconfig.json` пустой; Nuxt обычно генерирует `.nuxt/tsconfig.json`, но стоит проверить, что проектные алиасы и проверки типов настроены ожидаемо.
- `vitest.config.ts` пустой, хотя `package.json` задаёт `test: vitest run`. Заполните конфигурацию и добавьте минимальные тесты после появления логики; сейчас тестовый запуск может завершиться ошибкой конфигурации или отсутствия тестов.
- ESLint не указан среди зависимостей/скриптов; не рассчитывайте на `lint`-команду, пока команда её не добавит.
- `package.json` указывает `prepare: husky`, а hooks пока могут отсутствовать. Если установка пакетов падает на необязательной настройке Git hooks, согласуйте с командой исправление, не отключая проектные проверки молча.

## Локальный запуск

Из каталога `frontend/admin-panel`:

```bash
npm install
npm run dev
```

Если запуск сообщает об отсутствующих модулях, сначала сверьте `modules` в `nuxt.config.ts` с созданными каталогами и их entrypoint-файлами. Не маскируйте ошибку случайными пустыми страницами без согласования структуры с командой.

Сборка и тестовый скрипт:

```bash
npm run build
npm run test
```

Команды описывают предусмотренный workflow; тестовый конфиг сейчас пустой и может потребовать настройки перед использованием.

## Критерии готовности MVP

- Приложение запускается локально и собирается с согласованной конфигурацией.
- Сотрудник видит только доступные ему разделы и объекты; backend подтверждает все права.
- Список устройств показывает состояние, доступность и время данных.
- Карточка устройства корректно обрабатывает loading/empty/error/offline.
- Для выбранного устройства можно отправить согласованную команду и увидеть ответ сервера.
- API URL конфигурируется вне исходного кода; секретов и реальных пользовательских данных в Git нет.
- README/командные заметки объясняют запуск и необходимые переменные окружения без значений секретов.
