# IoT Integration Service — план работ

Этот сервис связывает веб-приложение УК с Ujin и другими IoT-платформами. Документ — точка входа для разработки сервиса; сначала согласуйте внешний контракт с автором админ-панели и владельцем сервиса авторизации.

## Зона ответственности

Сервис должен:

- регистрировать/связывать устройства с объектами и помещениями УК;
- получать телеметрию от платформ и приводить её к общей модели;
- отдавать панели актуальное состояние и историю сигналов;
- принимать команды пользователя, проверять доступ и отправлять их в нужную платформу;
- сообщать о недоступности интеграции, ошибках доставки и устаревших данных.

Сервис не должен владеть учётными записями пользователей и выпуском токенов: это зона `backend/auth`. Панель общается с сервисом по согласованному API, а не напрямую с Ujin. Не связывайтесь с реальным стендом без выданных командой доступов и тестового объекта.

## Предлагаемый порядок работ

### 1. Зафиксировать контракт между сервисами

До реализации согласуйте с командой:

- как идентифицируются организация УК, объект, помещение, устройство и сигнал;
- как auth передаёт identity и роли (JWT или проверенные gateway-заголовки);
- какие роли могут читать телеметрию, регистрировать устройства и отправлять команды;
- формат ошибок, пагинацию, фильтры и даты в UTC;
- API, который будет использовать админ-панель.

Минимальные API-операции для обсуждения: список устройств с фильтрами по объекту/помещению, получение состояния и истории устройства, отправка команды, регистрация/отвязка устройства. Зафиксируйте согласованную схему запросов и ответов в OpenAPI или `docs/` до параллельной реализации клиента панели.

### 2. Восстановить запускаемый каркас

Текущий `app/main.py` уже задаёт FastAPI lifespan, health router, API router и метрики, но часть импортируемых пакетов не создана. Также конфигурация использует `/app/shared`, которого нет в этом репозитории. Сначала проверьте и решите вместе с командой, откуда берётся shared-код и как сервис запускается локально и в контейнере. Не добавляйте заглушки, которые маскируют отсутствующие обязательные зависимости.

Рекомендуемая структура внутри `app/` (подстройте под существующий шаблон проекта):

```text
app/
  api/v1/                 # HTTP-маршруты и схемы запросов/ответов
  core/                   # настройки, auth-зависимости, ошибки, БД
  models/                 # внутренние сущности и таблицы, если нужна БД
  integrations/           # адаптеры внешних платформ (ujin/...)
  services/               # бизнес-операции и маршрутизация команд
  repositories/           # доступ к данным, если используется БД
  routers/                # health и системные маршруты
  main.py
```

Не помещайте платформенную бизнес-логику в HTTP-роуты: роут принимает/проверяет запрос, сервис выполняет операцию, адаптер общается с внешней платформой.

### 3. Описать общую модель IoT

Сделайте внутренний формат, не зависящий от названий полей конкретного вендора. Для старта определите сущности `Integration`, `Device`, `Signal` и `Command` (не обязательно все хранить в БД сразу). Зафиксируйте стабильные идентификаторы и связь с организацией/объектом/помещением.

У сигнала должны быть как минимум имя, тип/значение, единица измерения (если применимо), время измерения, время получения, доступность/качество и признак доступности записи. Не смешивайте время последнего получения с временем, когда устройство измерило значение.

### 4. Реализовать первый вертикальный сценарий на эмуляторе

Начните с чтения состояния одного устройства и отправки одной команды. Эмулятор — безопасный источник для локальной разработки; он не требует живого оборудования.

Из корня репозитория:

```powershell
cd backend/emulators
python main.py leak --port 8099
```

Откройте `http://localhost:8099` для локальной панели устройства. Изучите `core.py` (сигналы и модель устройства), `ujin_client.py` (обмен с Ujin), `live_loop.py` (получение команд) и `devices/leak_sensor.py`. Начните с dry-run/локального режима. Доступ к внешнему тестовому стенду включайте только с выданными параметрами.

Устройство/адаптер не должен менять общую модель данных в зависимости от конкретной платформы. Первую интеграцию используйте как адаптер к общему интерфейсу, чтобы впоследствии добавлять платформы без переписывания API.

### 5. Добавить надёжность и границы доступа

- Проверяйте доступ пользователя к организации и объекту на каждом запросе; роль сама по себе не заменяет проверку tenant/ресурса.
- Не принимайте `user_id`, роль или `organization_id` от клиента как доверенные значения. Получайте их из проверенной identity, согласованной с auth/gateway.
- Секреты, токены платформ и пароли БД храните в переменных окружения/secret store; не коммитьте их, не отдавайте в API и не пишите в логи.
- Для команд добавьте проверку типа/диапазона сигнала, тайм-аут, понятный результат доставки и корреляционный ID. Повтор команды не должен неожиданно выполнить действие дважды: согласуйте идемпотентность.
- Для внешних запросов предусмотрите тайм-ауты, ограниченные повторы с задержкой и явное состояние `unknown/offline`; не показывайте старое значение как свежее.
- Логи должны помогать диагностике по integration/device/request ID, но не содержать токены и персональные данные.

### 6. Довести вертикальный срез

Для первого сценария должны быть понятны и продемонстрированы цепочки:

1. панель запрашивает устройства пользователя;
2. сервис проверяет identity и доступ к объекту;
3. адаптер получает/нормализует состояние;
4. панель показывает значение, время обновления и доступность;
5. команда проходит серверную проверку прав и схемы сигнала;
6. адаптер отправляет команду, сервис возвращает подтверждённый статус или ошибку.

После этого расширяйте историю, регистрацию, дополнительные типы устройств и другие платформы.

## Текущие файлы и ограничения

- `app/main.py` — начатый FastAPI entrypoint.
- `app/core/config/settings.py` — использует базовые настройки из `/app/shared`; без доступного shared-пакета импорт может не работать.
- `app/core/dependencies/integration.py` — набросок JWT/gateway identity; контракт нужно сверить с auth-сервисом. Проверяйте права на ресурс, а не только роль.
- `app/core/database/` и `migration/` — заготовки SQLAlchemy/Alembic; сначала решите, какие данные сервис действительно хранит.
- `requirements.txt` — зависимости Python-сервиса.
- `../emulators/` — существующие модели устройств, Ujin-клиент и примеры протокола; это dev-инструмент, а не production API сервиса.
- `../../docs/iot-hackathon/` — материалы по API, pull-клиенту и протоколу Ujin. Часть документов описывает ограничения конкретного хакатонного стенда; проверяйте применимость к текущей среде.

## Минимальный чек-лист готовности первой версии

- Сервис запускается локально по описанной команде и отдаёт health-check.
- OpenAPI отражает согласованный контракт панели.
- Есть один сквозной сценарий «прочитать состояние → отправить команду» через эмулятор.
- Неавторизованный пользователь и пользователь без доступа к объекту получают отказ.
- Ошибки/тайм-ауты внешней платформы видны клиенту как контролируемое состояние.
- Конфигурация и секреты поступают извне; README содержит безопасные примеры без настоящих токенов.
