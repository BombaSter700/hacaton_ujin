# Тестовый VPS: сборка и деплой

## Что разворачивается

`compose.staging.yml` — отдельный стенд из PostgreSQL 18, ClickHouse, Redis,
KrakenD, auth и контейнера с девятью эмуляторами. Панель и integration пока
не включены: их сборка и запуск ещё не готовы.

Auth и эмуляторы собираются в GitHub Actions и публикуются в
`ghcr.io/programmisto/programmisto_auth` и `programmisto_emulators`.
Тег релиза — `sha-<полный SHA коммита>`, без использования `latest` при деплое.
На VPS сборки нет: исходники, тесты и миграции с хоста не монтируются в auth;
код и миграции уже находятся в образе.

## CI/CD

- PR в `main`: проверки Python, Bake и Compose, тесты auth с PostgreSQL 18,
  тесты эмуляторов, сборка двух образов без публикации.
- Push в `main`: те же проверки, затем публикация образов в GHCR.
- Run workflow на `main`, `deploy=false`: проверки и публикация, без деплоя.
- Run workflow на `main`, `deploy=true`: после проверок и публикации выполняется
  деплой в GitHub Environment `staging`.

В ручном запуске выбирается архитектура VPS: `linux/amd64` или `linux/arm64`.
Автоматические сборки используют `linux/amd64`. Сборки одного SHA для разных
архитектур перезаписывают тот же тег: для одного VPS выбирайте его архитектуру
постоянно. Мультиархитектурный manifest пока не собирается.

Репозиторий должен иметь право публиковать пакеты namespace `programmisto`.
Workflow запрашивает `packages: write` только у job сборки. Для существующего
GHCR-пакета предоставьте этому репозиторию доступ в настройках пакета.

## Подготовка сервера

Нужен Linux VPS с Docker Engine, Compose v2 с поддержкой `--wait`, Bash,
`tar`, `flock`, `realpath` и SSH. Пользователь деплоя должен иметь доступ к Docker
и право записи в каталог стенда. Требование входить именно как root убрано.
Настроенные лимиты памяти шести контейнеров суммарно около 3,25 ГБ;
для первого стенда предусмотрите запас для ОС, сборку на VPS выполнять не нужно.

Создайте каталог, принадлежащий пользователю деплоя, например
`/srv/programmisto`. Скопируйте туда `.env.staging.example` под именем
`.env.staging`, замените все `CHANGE_ME` и установите права 600.
Шаблон и реальные секреты — разные файлы; реальный `.env.staging` не коммитьте.

`AUTH_DATABASE_URL` должен содержать тот же пароль, что `POSTGRES_PASSWORD`;
спецсимволы в URL кодируются. Внутренний адрес — `programmisto_postgres:5432`,
база по умолчанию — `auth_db`. JWT-ключ — случайная строка от 32 символов.
Пароли Redis и ClickHouse также задаются в `.env.staging`.

Если пакеты GHCR приватные, заранее выполните на VPS `docker login ghcr.io`
от имени пользователя деплоя, используя отдельный токен с `read:packages`.
Workflow не передаёт свой `GITHUB_TOKEN` на сервер. Образы должны быть доступны
этому пользователю; для публичных пакетов вход обычно не нужен.

## GitHub Environment staging

Создайте Environment `staging`; при необходимости задайте reviewers для ручного
подтверждения. Сам workflow не включает автоматический деплой после push.

Secrets окружения:

| Имя | Значение |
| --- | --- |
| `STAGING_HOST` | DNS-имя или IPv4 VPS, без протокола |
| `STAGING_USER` | SSH-пользователь |
| `STAGING_SSH_KEY` | Приватный ключ этого пользователя |
| `STAGING_SSH_KNOWN_HOSTS` | Проверенная запись SSH host key сервера |

Variables окружения:

| Имя | По умолчанию |
| --- | --- |
| `STAGING_SSH_PORT` | `22` |
| `STAGING_DEPLOY_PATH` | `/srv/programmisto` |

Путь абсолютный, без пробелов. Host key сверяйте через доверенный канал;
workflow не принимает его автоматически через `ssh-keyscan`.
Для нестандартного порта запись known_hosts должна соответствовать
`[hostname]:port`. Перед первым запуском файл `.env.staging` уже должен
находиться на VPS. Сам workflow также должен попасть в `main`, чтобы появился
ручной запуск в GitHub Actions.

## Как устроен релиз

В `releases/<SHA>-<run>-<attempt>/` загружается архив только с:

- `compose.staging.yml`;
- конфигом KrakenD;
- init-скриптами PostgreSQL/ClickHouse и `pg_hba.conf`;
- скриптом `scripts/deploy-staging.sh`.

Секреты и исходники в архив не входят. Скрипт создаёт `.image.env` с registry/tag,
читает общий `.env.staging`, получает образы и запускает Compose с постоянным
именем проекта `programmisto-staging`. Это сохраняет одни и те же именованные тома
между релизами. Миграции auth применяются его entrypoint до запуска API.

`up --wait` ожидает health всех шести сервисов. Только после успеха ссылка
`current` переключается на новый релиз, `previous` сохраняет предыдущий.
GitHub concurrency и серверный `flock` исключают параллельный деплой.
Скрипт не делает `down -v`, очистку образов и удаление старых релизов.

При ошибке контейнеры могут оказаться частично обновлёнными; ссылка `current`
не меняется, но это не автоматический откат. Посмотрите `docker compose ps`
и логи на VPS перед повторным запуском.

## Доступ к API и устройствам

Порты опубликованы только на localhost VPS. PostgreSQL, Redis и ClickHouse
вообще не публикуются на хост. Публичный reverse proxy, домен и TLS
настраиваются отдельно. KrakenD проксирует текущие API auth на порту 8080;
маршруты и настройки описаны в [README шлюза](../../infra/krakend/README.md).

Для тестирования с компьютера:

```bash
ssh -L 8001:127.0.0.1:8001 -L 8098:127.0.0.1:8098 -L 8099:127.0.0.1:8099 deploy@VPS
```

После подключения:

- auth health: `http://localhost:8001/health/ready`;
- Swagger: `http://localhost:8001/api/docs`, если на VPS задано `AUTH_DEBUG=true`;
- общий health эмуляторов: `http://localhost:8098/health`;
- термостат: `http://localhost:8099/`.

Для остальных устройств добавьте туннели портов 8100–8107.

## Ручной повтор и возврат на предыдущий образ

На сервере, после успешной публикации нужного SHA:

```bash
cd /srv/programmisto/current
bash scripts/deploy-staging.sh /srv/programmisto sha-FULL_40_CHARACTER_COMMIT_SHA ghcr.io/programmisto
```

Замените пример на настоящий полный SHA. Для отката используйте каталог
`previous` и соответствующий ему SHA. Обратная совместимость схемы БД должна
сохраниться: смена образа не отменяет уже применённые миграции, автоматического
`alembic downgrade` нет. Перед изменениями существующих данных сделайте резервную копию.

## Локальная проверка файлов

```powershell
python scripts/sync-bake.py --check
python scripts/check-staging.py
```

HCL — основной файл сборки. После его изменения обновите JSON:

```powershell
python scripts/sync-bake.py
```

Скрипт генерирует эквивалентный JSON с переменными и проверяет оба варианта через
`bake --print`, включая переопределение тега и архитектуры. CI отклоняет расхождения.
Ни одна из этих команд не публикует образы и не подключается к VPS.
