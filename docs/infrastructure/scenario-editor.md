# Конструктор описаний и редактор сценариев

## Что доступно

В карточке устройства откройте «Настроить описание». Можно изменить название устройства,
названия сигналов, тип значения (число, текст, да/нет), единицу измерения, диапазон команды
и разрешение записи. API сохраняет всё одной транзакцией.

Конструктор работает с уже подключёнными типами устройств. Внешние идентификаторы,
набор физических сигналов и адрес устройства через форму не меняются. Если оборудование
предоставляет сигнал только для чтения, разрешить запись нельзя. При выборе типа нужно
учитывать фактические данные устройства: форма не перепрограммирует оборудование.
Повторный импорт обновляет подключение, но сохраняет ручные описания сигналов.

Раздел «Сценарии» доступен администратору. Объекты и устройства загружаются из API.
Единственный объект выбирается автоматически. Для сценария задаются:

- название и описание;
- условие по сигналу: устройство, сигнал, сравнение и типизированное значение;
- условие времени суток: начало, конец, часовой пояс IANA;
- способ объединения: все условия или хотя бы одно;
- действия: доступные команды выбранных устройств и значения;
- признак активности.

До 10 условий и 10 действий на правило. Условия и действия могут ссылаться только на
устройства выбранного объекта. Числовые сравнения недоступны для текста и логических значений.
Диапазон сигнала ограничивает команду; порог условия может выходить за этот диапазон.

Временной контракт для следующего этапа: начало включительно, конец исключительно;
интервал с началом позже конца проходит через полночь, одинаковые границы означают весь день.

## Важная граница этапа

Сценарии сохраняются в PostgreSQL, их можно читать, редактировать, включать, выключать и удалять.
Автоматического исполнения пока нет. Признак enabled — сохранённая настройка будущего движка.
Создание или включение правила не отправляет команды устройствам.

Редактор не заменяет следующий этап: проверку условий, расписания, приоритет аварий,
защиту от циклов, исполнение и журнал запусков.

## Пример

1. Откройте /admin/scenarios.
2. Создайте «Дневной микроклимат».
3. Добавьте время 08:00–22:00, Europe/Moscow.
4. Добавьте условие «термостат → Температура → меньше → 20».
5. Выберите «Выполнены все условия».
6. Добавьте действие «термостат → Цель → 24».
7. Сохраните. Откройте правило повторно, чтобы проверить сохранённые поля.

Карточка устройства по-прежнему позволяет отправить команду вручную и проверить подтверждение.

## API через KrakenD

| Метод | Путь | Назначение |
|---|---|---|
| PUT | /api/v1/devices/{id}/definition | Сохранить название и все существующие описания сигналов |
| GET | /api/v1/scenarios/?object_id=UUID&skip=0&limit=50 | Список: items и total |
| POST | /api/v1/scenarios/ | Создать правило, ответ 201 |
| GET | /api/v1/scenarios/{id} | Получить правило |
| PUT | /api/v1/scenarios/{id} | Полностью обновить; expected_revision обязателен |
| PATCH | /api/v1/scenarios/{id} | Изменить enabled; expected_revision обязателен |
| DELETE | /api/v1/scenarios/{id}?expected_revision=N | Удалить, ответ 204 |

Все операции требуют Bearer-сессию администратора через auth.
Входные схемы запрещают неизвестные поля, NaN/Infinity и неверные типы значений.
Правило возвращает revision; конфликт версий даёт 409 и требует повторной загрузки.
Включение повторно проверяет актуальные ссылки и команды.

Изменение описания устройства отклоняется с 409, если оно делает активный сценарий
некорректным. Сначала выключите или исправьте такой сценарий. Неактивный сценарий также
пройдёт проверку перед следующим включением.

PUT описания принимает name и signals. Каждый сигнал: id, name, value_type, unit,
is_writable, min_value, max_value. Передаются все существующие сигналы устройства.
В ответах Signal появились value_type, source_is_writable и is_customized.

## Миграция и проверка

003_device_editor_scenarios добавляет типы и признаки настройки сигналов, таблицу scenarios.
Старые устройства и команды сохраняются. Для существующих сигналов тип определяется по
метаданным; повторный импорт уточняет его по данным эмулятора, если сигнал не настраивался вручную.

Entry point применяет миграцию автоматически. На VPS перед обновлением сделайте резервную копию
integration_db; порядок обновления — в [integration-gateway.md](integration-gateway.md).
После обновления пересоздайте KrakenD, поскольку добавились маршруты и метод PUT в CORS.

Локально:

```bash
docker compose up -d --build --wait --wait-timeout 180 programmisto_integration programmisto_admin_panel
docker compose up -d --no-deps --force-recreate --wait programmisto_krakend
python backend/integration/tests/smoke_editors.py
```

Сквозной тест создаёт временные аккаунт, парк и правило, проверяет сохранение после импорта,
CRUD, версии и ограничения, затем удаляет свои данные. Команды оборудованию он не отправляет.

Проверки схем находятся в backend/integration/tests/test_scenario_validation.py,
проверки клиентского разбора значений — frontend/admin-panel/tests/signal-values.test.ts.
