# Инфраструктура проекта

Подготовка VPS, GitHub Actions и релизы: [тестовый стенд staging](staging.md).

Локальная инфраструктура приложения управляющей компании описана в
[`docker-compose.yml`](../../docker-compose.yml). Сейчас запускаются хранилища
и шлюз. Прикладные сервисы ещё разрабатываются: готовность инфраструктуры
не означает готовность полного IoT-сценария.

## Сервисы

| Сервис Compose | Образ | Назначение |
| --- | --- | --- |
| `programmisto_postgres` | `postgres:18` | Пользователи, администраторы, роли, организации, здания, реестр устройств и связи между ними |
| `programmisto_clickhouse` | `clickhouse/clickhouse-server:25.3` | История показаний, события устройств и аудит |
| `programmisto_redis` | `redis:7-alpine` | Хранилище для последнего состояния устройств и будущей очереди телеметрии |
| `programmisto_krakend` | `krakend:2.13.11` | API-шлюз для auth, пользователей и сессий; [маршруты и настройки](../../infra/krakend/README.md), собственный health `/__health` |
| `programmisto_emulators` | Локальная сборка на Python 3.12 | Девять устройств в одном контейнере, общий `/health` на порту 8098 |

Предполагаемый поток после реализации обработки телеметрии:

```text
Ujin / эмуляторы → сервис приёма → очередь → обработчик → ClickHouse: история
                                                └───→ Redis: последнее состояние

PostgreSQL: пользователи, права, объекты и реестр устройств
```

Redis Streams, обработчик очереди и запись потока из integration в ClickHouse
пока не подключены.

## Запуск и остановка

Нужны Docker с Linux-контейнерами и Docker Compose с поддержкой `--wait`.
Для автоматической проверки дополнительно нужен Python 3.
Все команды выполняются из корня репозитория.

```powershell
# Проверить конфигурацию без запуска
docker compose config --quiet

# Запустить инфраструктуру и дождаться healthcheck
docker compose up -d --wait --wait-timeout 180

# Посмотреть состояние и логи
docker compose ps
docker compose logs --tail 100

# Проверить шлюз с хоста
curl.exe --fail http://localhost:8080/__health

# Остановить контейнеры, сохранив данные
docker compose down
```

При изменении `KRAKEND_PORT` используйте соответствующий порт в URL.
По умолчанию запускаются четыре инфраструктурных сервиса и флот эмуляторов.
Профиль `backend` содержит auth и integration, профиль `frontend` — панель
администратора. Они пока не готовы к запуску: backend требует отсутствующие
модули приложений, пакет `shared` и конфигурацию/миграции Alembic;
панель — Dockerfile и Nuxt-модули.

## Флот смарт-устройств

Для разработчика integration: [HTTP-контракт, сигналы всех устройств и примеры команд](emulators/README.md).

Контейнер `programmisto_emulators` использует существующий Python-код из
[`backend/emulators`](../../backend/emulators/). Модуль `fleet.py` запускает
девять независимых процессов с устройствами из `fleet.json`. Каждый изменяет
показания во времени, принимает команды и предоставляет веб-панель.
Внешние запросы Ujin работают в dry-run; токены и доступ к стенду
для этого запуска не нужны. Данные в Redis и ClickHouse он пока не записывает.

```powershell
docker compose up -d --build --wait
curl.exe --fail http://localhost:8098/health
curl.exe --fail http://localhost:8099/state
curl.exe --fail http://localhost:8099/declaration

# Изменить целевую температуру
curl.exe --fail -X POST http://localhost:8099/command -d "signal=target_temp&value=25"

# Остановить эмулятор
docker compose stop programmisto_emulators
```

Общий health: `http://localhost:8098/health`, список: `/devices` на том же порту.
Health возвращает HTTP 200 только если каждый процесс жив и его `/state` отвечает;
при недоступности хотя бы одного устройства возвращает HTTP 503. Если процесс
устройства завершается, supervisor останавливает весь флот с ошибкой, чтобы
политика Docker перезапустила контейнер. SIGTERM останавливает дочерние процессы.

| Устройство | Серийный номер | Порт панели, `/state` и `/declaration` |
| --- | --- | --- |
| Термостат | `local-thermostat-001` | 8099 |
| Датчик протечки | `local-leak-001` | 8100 |
| Хаб датчиков | `local-hub-001` | 8101 |
| Счётчик | `local-counter-001` | 8102 |
| Свет | `local-light-001` | 8103 |
| Вентиляция | `local-ventilation-001` | 8104 |
| Пожарный датчик | `local-fire-001` | 8105 |
| Шлагбаум | `local-barrier-001` | 8106 |
| Лифт | `local-elevator-001` | 8107 |

Например, панель термостата: `http://localhost:8099/`. Внутри сети Compose:
`http://programmisto_emulators:8099/state`. Порты хоста привязаны к localhost;
интерфейс эмулятора не имеет аутентификации и предназначен для локального стенда.

Настройки через корневой `.env`:

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `EMULATOR_INTERVAL` | `1` | Реальное время между шагами модели, в секундах; используйте положительное значение |

Состав, серийные номера и порты задаются в
[`fleet.json`](../../backend/emulators/fleet.json). Имена семейств соответствуют
реестру устройств; номера и порты должны быть уникальными. Порт 8098 зарезервирован
для health. При добавлении портов за пределами 8099–8107 измените публикацию
в Compose. Для применения конфигурации или кода пересоберите контейнер с `--build`.
Состояние моделей хранится в памяти и сбрасывается при рестарте.
Интервал меняет темп симуляции: каждый шаг модели равен одной условной секунде.

Запуск существующих тестов в контейнере:

```powershell
docker compose run --rm --no-deps --entrypoint python programmisto_emulators -m unittest discover -s backend/emulators/tests
```

## Сеть

Все сервисы подключены к bridge-сети `app-network`. Внутри неё используйте
имена сервисов Compose; `localhost` внутри контейнера означает сам контейнер.

| Компонент | Внутренний адрес | Доступ с хоста по умолчанию |
| --- | --- | --- |
| PostgreSQL | `programmisto_postgres:5432` | Не опубликован |
| ClickHouse HTTP | `programmisto_clickhouse:8123` | Не опубликован |
| ClickHouse native | `programmisto_clickhouse:9000` | Не опубликован |
| Redis | `programmisto_redis:6379` | `127.0.0.1:6379` |
| KrakenD | `programmisto_krakend:8080` | `http://127.0.0.1:8080` |

## Переменные окружения

Настройки читаются из окружения и корневого `.env`. Для локальной проверки
достаточно значений по умолчанию, поэтому `.env` может быть пустым.

| Переменная | Значение по умолчанию | Назначение |
| --- | --- | --- |
| `POSTGRES_USER` | `ujin` | Пользователь PostgreSQL |
| `POSTGRES_PASSWORD` | `local-dev-password` | Пароль PostgreSQL |
| `POSTGRES_DB` | `ujin` | Начальная база PostgreSQL |
| `AUTH_DB_NAME` | `auth_db` | База метаданных auth |
| `INTEGRATION_DB_NAME` | `integration_db` | База метаданных integration |
| `CLICKHOUSE_USER` | `ujin` | Пользователь ClickHouse |
| `CLICKHOUSE_PASSWORD` | `local-clickhouse-password` | Пароль ClickHouse |
| `CLICKHOUSE_DB` | `iot` | База телеметрии и событий |
| `REDIS_PASSWORD` | `local-redis-password` | Пароль Redis |
| `REDIS_PORT` | `6379` | Порт Redis на localhost хоста |
| `KRAKEND_PORT` | `8080` | Порт шлюза на localhost хоста |

Пароли по умолчанию предназначены для локальной разработки. Для общего стенда
задайте свои секреты через окружение или `.env`, не добавляя их в Git.
Изменение переменных PostgreSQL не меняет пользователя, пароль и имена баз
в уже созданном томе: для этого нужны отдельные SQL-команды.

## Сохранение данных

| Именованный том | Путь в контейнере | Содержимое |
| --- | --- | --- |
| `postgres_data` | `/var/lib/postgresql` | Данные PostgreSQL 18 |
| `clickhouse_data` | `/var/lib/clickhouse` | Таблицы ClickHouse |
| `clickhouse_logs` | `/var/log/clickhouse-server` | Логи ClickHouse |
| `redis_data` | `/data` | Файлы сохранения Redis |

Compose добавляет к именам томов префикс проекта. Данные сохраняются при рестарте,
пересоздании контейнеров и `docker compose down`. Команда `docker compose down -v`
удаляет тома и данные; для обычной остановки она не нужна. Именованные тома
не заменяют резервное копирование: автоматические копии этим Compose не настроены.

### PostgreSQL

[`init-databases.sh`](../../infra/postgres/init-databases.sh) создаёт базы auth
и integration при первой инициализации пустого тома.
[`pg_hba.conf`](../../infra/postgres/pg_hba.conf) задаёт правила подключения.
Метаданные, связи объектов и права доступа остаются в PostgreSQL и прикладном API.

### ClickHouse

[`init-databases.sh`](../../infra/clickhouse/init-databases.sh) создаёт базу
`CLICKHOUSE_DB` и три таблицы:

| Таблица | Содержимое | Срок хранения |
| --- | --- | --- |
| `telemetry` | Числовые показания; логические значения кодируются как 0/1 | 30 дней от `measured_at` |
| `device_events` | Тревоги, изменения доступности, результаты команд | Год от `occurred_at` |
| `audit_events` | События сервисов с контекстом пользователя и сущности | Два года от даты `occurred_at` |

Телеметрия содержит UUID организации, здания, устройства и события, метрику,
значение, единицу измерения, качество и источник. `measured_at` — время измерения,
`received_at` — время получения. Временные поля используют UTC.
`payload` и `context` содержат JSON в строковом виде; формат проверяет приложение.

Таблицы используют месячные разделы и `ReplacingMergeTree(received_at)`.
Повторная доставка должна сохранять весь ключ сортировки, включая ID события
и исходное время измерения/события. Замена версий происходит при фоновых слияниях:
до слияния точные запросы требуют `FINAL` или агрегации с учётом версий.
TTL также применяется асинхронно. Минутные и часовые агрегаты пока не созданы.

Init-скрипт проверяет имя базы и завершает работу при ошибке. Автоматически
он выполняется при первом запуске с пустым томом. Повторный ручной вызов
создаёт отсутствующие таблицы и индексы:

```powershell
docker compose exec -T programmisto_clickhouse bash /docker-entrypoint-initdb.d/init-databases.sh
```

`IF NOT EXISTS` не обновляет структуру существующей таблицы. Изменения типов,
ключей и TTL оформляйте отдельными миграциями. Не удаляйте том ради обновления
схемы. Shell-файлы должны иметь окончания строк LF, что закреплено
в [`.gitattributes`](../../.gitattributes).

ClickHouse не проверяет внешние ключи к PostgreSQL. Проверку принадлежности
устройства организации, доступа пользователя, значений и времени выполняет API
или сервис приёма.

### Redis

Включены AOF и `appendfsync everysec`. При штатном рестарте данные восстанавливаются;
при сбое ОС или питания возможна потеря примерно последней секунды записей.
Лимит данных Redis — 128 МБ, памяти контейнера — 256 МБ.
Политика `noeviction` не вытесняет записи автоматически: при достижении лимита
команды записи могут возвращать ошибку.

Для будущей очереди нужны обработка ошибок, контроль размера, повторная доставка
и подтверждение сообщения после успешного сохранения. Для кеша состояния
и очереди используйте разные префиксы ключей и отдельные правила срока жизни.
Само наличие Redis пока не создаёт очередь и не гарантирует доставку.

## Проверки и диагностика

Healthcheck проверяет доступность PostgreSQL, `PONG` Redis, доступ к таблице
`telemetry` в ClickHouse и `/__health` шлюза. Сквозная доставка IoT-событий
и производительность под нагрузкой этой проверкой не оцениваются.

```powershell
python scripts/smoke-infrastructure.py
```

Скрипт проверяет Compose, запускает инфраструктуру, проверяет синтаксис и повторное
выполнение ClickHouse init, наличие трёх таблиц, запись и чтение тестовых данных.
Затем перезапускает Redis и ClickHouse и проверяет сохранность записей.
После успеха удаляет тестовую таблицу `_infrastructure_smoke` и ключ
`ujin:smoke:infrastructure`. Эти имена зарезервированы для проверки; TTL ключа —
300 секунд. При ошибке таблица может остаться для диагностики.

Проверка вызывает кратковременную недоступность двух хранилищ и предназначена
для локального стенда. Успех обозначается строкой `PASS`.

Если контейнер не стал healthy, начните с логов:

```powershell
docker compose logs --tail 100 programmisto_clickhouse programmisto_redis
```

Проверьте доступность Docker Engine, занятость портов 8080/6379, наличие файлов
bind-mount и окончания строк shell-файлов. Если таблицы не появились в существующем
томе ClickHouse, изучите ошибку init и повторите скрипт после исправления.
Лимиты ресурсов рассчитаны на локальную проверку; производительность оценивайте
отдельно на ожидаемой частоте и объёме IoT-данных.
